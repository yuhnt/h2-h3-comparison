Measurement report · Advanced Networking

HTTP/2 vs HTTP/3 under emulated delay and packet loss

Two experiments against nginx over TCP (HTTP/2) and QUIC (HTTP/3), with delay and loss injected on the server using tc netem: one isolates HTTP/3's protocol advantage, the other checks whether today's servers and clients let HTTP/3 replace HTTP/2.

Summary

What the measurements show

The two demos answer different questions. Demo 2 keeps the client, connection and workload identical and changes only the protocol, so it shows what HTTP/3 is designed to fix: head-of-line blocking between streams. Demo 1 fetches single objects through several real clients, so its results depend as much on how nginx and each client implement HTTP/3 as on the protocol; it shows whether HTTP/3 can already take over from HTTP/2.

Demo 2 · protocol advantage

HTTP/3 removes head-of-line blocking

10.5× faster at 12% loss20 × 1 MB on one verified connection · HTTP/3 6.05 s vs HTTP/2 63.7 s

HTTP/3 overtakes HTTP/2 from 4% loss (1.85×) and pulls far ahead at 8% (5.5×). From 0% to 12% loss the HTTP/2 batch slows 141×, HTTP/3 only 6×, because every lost TCP segment stalls all twenty streams.

Demo 1 · protocol advantage

Faster connection setup on a delayed path

62 ms vs 113 ms10 KB at 25 ms delay · 115 vs 213 ms at 50 ms

The one place a single request already benefits: QUIC combines the transport and TLS 1.3 handshakes, so a small object arrives about 45% sooner once delay is added, with or without loss.

Demo 1 · deployment

Single large downloads still favour HTTP/2

18.8 s vs 33.8 s10 MB at 25 ms delay and 2% loss · curl

With one stream there is no blocking to remove, and the kernel's TCP recovers from loss faster than user-space QUIC. At 50 ms and 2% loss four of five HTTP/3 requests passed 60 s. The same protocol varied by client: aioquic took 26.6 s where curl took 33.8 s.

Demo 1 · deployment

Not yet a drop-in replacement

Only curl worked out of the boxWget/wget2: no HTTP/3 · aioquic: library only · quiche-client: debug build · Proxygen: too heavy to build

nginx needed three HTTP/3 defaults changed to perform well, the HTTP/3 endpoint still has to serve TCP and advertise itself through Alt-Svc, and most download tools lacked usable HTTP/3 support. HTTP/3 complements HTTP/2 rather than replacing it.

nginx: HTTP/3 server (nginx/http3/nginx.conf)

http {
    quic_retry off;
    server {
        listen 8444 ssl;              # TCP, HTTP/2 fallback
        listen 8444 quic reuseport;   # UDP, QUIC
        http2 on;
        http3 on;
        ssl_protocols TLSv1.2 TLSv1.3;
        ssl_session_tickets off;
        quic_gso off;
        http3_stream_buffer_size 16m;
        add_header Alt-Svc 'h3=":8444"; ma=86400' always;
    }
}

Network emulation

Delay and loss are applied to the server's outgoing traffic from ports 8443 and 8444 only, using a priority qdisc whose fourth band holds a netem qdisc. Server-to-client packets carry the payload, so a delay of D adds about D to every round trip; loss is random and independent per packet. SSH and other traffic stay in the normal bands.

The condition is applied with scripts/set-network-condition-linux.sh, run through the netem helper container over SSH from the client before each condition. The client then checks that time to first byte matches the delay and stops rather than record results under the wrong label.

Demo 2 · Protocol advantage

Twenty parallel streams on one connection

This is the protocol comparison. Client (curl), server (nginx), connection count (one), workload (20 × 1 MB started together) and loss are identical for both protocols; only the transport underneath the streams changes. HTTP/2 multiplexes all streams over a single TCP byte stream, which must be delivered in order. HTTP/3 carries each stream separately inside QUIC, which recovers losses per stream.

curl reports for every transfer whether it opened a new connection, and each batch was checked to use exactly one connection for both protocols. This matters: an earlier run used curl's --parallel-immediate, which opens a separate connection per file, so it compared 20 independent connections and could not show head-of-line blocking. Those results were discarded.

Packet loss HTTP/2 batch HTTP/3 batch HTTP/2 per stream HTTP/3 per stream Speed-up Connections Failed

Under loss the per-stream average sits close to the batch time for both protocols (at 12%: 61.3 s vs 63.7 s over HTTP/2), so the streams finish at about the same moment. For HTTP/2 that is head-of-line blocking at work: all streams wait on the same stalled byte stream and share one congestion window that every loss shrinks. HTTP/3 streams also end together, but ten times sooner.

Demo 1 · Deployment check

Single requests through real servers and clients

A single request on a new connection uses one stream, so HTTP/3's stream independence has nothing to improve. What remains is the protocol's faster handshake, plus how well each implementation sends, receives and recovers data. Demo 1 therefore shows how today's software handles HTTP/3 in practice, and whether it can replace HTTP/2 for ordinary downloads.

Same protocol, different clients

The two HTTP/2 clients agree closely on large files (wget2 is faster on small files only because its timing starts after the TCP connection is open). The two HTTP/3 clients do not: aioquic, written in Python, is slower than curl without loss, yet with loss and delay it downloads 10 MB faster than curl. For HTTP/3 the choice of implementation still changes results as much as the network does, which is itself a sign of a younger ecosystem.

Discussion

Protocol advantages and deployment reality

Protocol · Demo 2

No head-of-line blocking between streams

HTTP/2 multiplexes streams over one TCP connection, which delivers bytes strictly in order, so a lost segment stalls all streams. QUIC recovers loss per stream and the other streams keep going. The benefit grows with the loss rate and the number of parallel streams.

20 × 1 MB on one connection, 0% → 12% loss: HTTP/2 0.45 → 63.7 s, HTTP/3 0.96 → 6.05 s

Protocol · Demo 1

Fewer round trips to set up a connection

HTTP/2 needs a TCP handshake, then a TLS 1.3 handshake, before the request. QUIC carries TLS inside its own handshake, so the request goes out one exchange earlier. On a delayed path the saved round trips dominate small requests.

10 KB at 50 ms: HTTP/2 213 ms vs HTTP/3 115 ms

Deployment · Demo 1

Mature kernel TCP against young user-space QUIC

For a single lossy stream, transfer time depends on how fast lost packets are detected and repaired. The Linux kernel's TCP has decades of tuning for exactly this; nginx's QUIC and curl's ngtcp2 run in user space and are far newer, and they fell behind by 1.8× or more.

10 MB at 25 ms · 2%: HTTP/2 18.8 s vs HTTP/3 33.8 s

Deployment · Demo 1

Uneven support across software

Among the tools tried, only curl offered ready-made HTTP/3; results for the same protocol differed widely between curl and aioquic; nginx needed tuning; and the HTTP/3 service still relies on a TCP endpoint for discovery and fallback.

10 MB at 50 ms · 2%: aioquic 52.6 s vs curl 4 of 5 runs over 60 s

Threats to validity

Limitations

  • Shared hardware. Both VMs run on one laptop and use 6 of its 8 hardware threads, so CPU contention can affect transfers that are CPU-bound, such as QUIC processing and the Python client.
  • One server implementation. Demo 2 uses curl and nginx only, and Demo 1's deployment findings cover the tools tried here; other servers (for example with a different QUIC stack) or clients may behave differently, as the aioquic results already show.
  • Emulated path. Delay and loss apply only to server-to-client packets, loss is uniform and independent with no bursts, and no bandwidth limit is set. Without shaping, HTTP/2 moves 10 MB in 0.21 s, about 400 Mbit/s.
  • Five runs. Medians with min and max limit the effect of outliers, but some ranges are wide, for example HTTP/3 10 MB at 50 ms without loss (0.73–5.1 s).
  • Timeouts. The true 10 MB HTTP/3 time at 50 ms · 2% is unknown beyond "over 60 s" for four of five runs.
  • Not covered. Connection resumption and 0-RTT (session tickets are off), connection migration, and loss on the client-to-server direction.

Conclusion

Conclusion

The protocol advantage is real. With client, server and workload held constant (Demo 2), HTTP/3's independent streams made a 20-stream batch on one connection 1.9× to 10.5× faster at 4% to 12% packet loss, while HTTP/2's batch time grew about 140-fold. Its combined transport and TLS handshake also made small requests about 45% faster on a delayed path.

HTTP/3 does not yet replace HTTP/2. Through real software (Demo 1), a single large download with loss took HTTP/3 roughly twice as long or more, because mature kernel TCP out-recovers today's user-space QUIC stacks. HTTP/3 support was uneven: one of the download tools tried worked out of the box, a Python client beat curl in some conditions, nginx needed tuning, and the HTTP/3 service still depended on TCP for discovery and fallback.

HTTP/3 is therefore best deployed alongside HTTP/2: it pays off for pages that load many objects over lossy or high-latency networks, while HTTP/2 remains the dependable path for everything else and for clients and networks that cannot use QUIC.
