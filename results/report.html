Summary

What the measurements show

HTTP/3 is not uniformly faster or slower. It wins where its design says it should: connection setup over a delayed path, and many parallel streams under heavy loss. It loses clearly on large single downloads, and part of that loss comes from this test bed rather than from the protocol (see why HTTP/3 lags on bulk transfers). All protocol comparisons below use curl for both protocols, so only the protocol changes.

HTTP/3 faster

Small requests over a delayed path

74 ms vs 94 msheaders-only request at 25 ms delay · 124 vs 171 ms at 50 ms

QUIC folds the transport and TLS 1.3 handshakes into one exchange, so a new connection needs one server round trip fewer. The gain grows with delay: 21% at 25 ms, 27% at 50 ms, and 36–41% for a 10 KB object.

HTTP/2 faster

Large single downloads

0.44 s vs 4.11 s10 MB at 25 ms delay, no loss · 9.3× slower over HTTP/3

HTTP/3 was slower for 10 MB in every condition: 2.9× with no delay, 7.6× at 50 ms. At 50 ms and 2% loss all five HTTP/3 requests hit the 60 s timeout, while HTTP/2 finished in 32.4 s.

Depends on size

The crossover sits between 100 KB and 500 KB

0.93× → 1.04×HTTP/3 ÷ HTTP/2 time at 50 ms, 100 KB → 500 KB

With delay and no loss, HTTP/3 is ahead up to about 100 KB, where handshake time dominates, and behind from 500 KB on, where sustained throughput dominates. Without delay HTTP/3 was never ahead (1.10–2.86×).

Depends on loss

20 parallel streams under heavy loss

1.49× faster at 12% lossbatch of 20 × 1 MB · HTTP/3 2.54 s vs HTTP/2 3.79 s

HTTP/3 trailed from 0% to 8% loss (0.52–0.70× as fast) but overtook HTTP/2 at 12%. From 0% to 12% loss the HTTP/2 batch time grew 7.6×, HTTP/3 only 2.8×: the signature of TCP head-of-line blocking.

Network emulation. Delay and random per-packet loss were applied with tc qdisc replace dev eth0 root netem delay D loss L limit 100000 inside both server containers, so only server-to-client packets are affected and a delay of D adds about D to every round trip. Segmentation offloads were turned off so netem handles real packet sizes; a check at 10% loss produced 11.0% TCP retransmissions.

Demo 1, single stream. Seven files (0 KB to 10 MB), each fetched five times on a fresh connection per client. The value is the mean of successful runs, from connection start to the last byte; a run over 60 s counts as failed.

Demo 2, multi-stream. Twenty 1 MB files fetched in parallel over one connection with curl --parallel, five times per protocol. The value is the mean batch completion time; the timeout is 120 s per transfer.

Discussion

Why HTTP/3 lags on bulk transfers here

The gap on large downloads is larger than the protocols' design alone would explain. Four properties of this test bed contribute, each supported by a measurement.

Docker Desktop relays the connections

nginx sees every client as 172.22.0.1. For HTTP/2 the relay terminates TCP, so lost segments are repaired on a short in-VM hop and Kali receives the bytes over a second, clean connection. QUIC datagrams pass through unchanged, so HTTP/3 recovers each loss end to end.

10 MB, 0 ms · 2% loss: HTTP/2 0.19 s vs HTTP/3 2.01 s

curl's HTTP/3 receive window grows slowly

With larger round trips the client's flow-control window, not the network, limits curl over HTTP/3. aioquic with 16 MB windows is faster despite being written in Python.

10 MB at 50 ms: curl HTTP/3 6.49 s vs aioquic 2.68 s

User-space QUIC vs kernel TCP

On a gigabit virtual link CPU cost decides throughput. TCP runs in the kernel; QUIC is processed per packet in nginx and relayed per datagram by Docker Desktop.

10 MB, no delay or loss: HTTP/2 0.16 s vs HTTP/3 0.45 s

Server defaults (corrected before the run)

nginx's 64k HTTP/3 stream buffer and Retry handshake cost HTTP/3 throughput and one round trip. Both were changed before the final measurements, so they explain earlier results but not the ones in this report.

10 MB at 25 ms with the 64k buffer: 5.6 s · in the final run: 4.11 s

Threats to validity

Limitations

  • Relay asymmetry. Docker Desktop terminates TCP but not QUIC, which favours HTTP/2 under loss. Running the server on a Linux VM without port forwarding would remove this.
  • Means of five runs. Per-run spread was not recorded, and single slow runs pull some means up, for example 10 KB over HTTP/2 at 50 ms · 2% loss: 728 ms against 216 ms at 0% loss.
  • One-directional, random loss. Delay and loss apply only to server-to-client packets, loss is uniform with no bursts, and there is no bandwidth limit on the ~1.1 Gbit/s link.
  • Incomplete matrix. 50 ms · 4% was not measured, and the true 10 MB HTTP/3 time at 50 ms · 2% is unknown beyond "over 60 s".
  • Client implementations. quiche-client is a debug build timed with process start-up; aioquic is Python. Protocol conclusions rest on curl.
  • Shared hardware. Client VM and server run on the same physical machine and compete for CPU.

Conclusion

Conclusion

In this test bed HTTP/3 delivered its two design advantages. It set up connections one round trip faster, which made small requests 21–41% quicker once delay was added. With twenty parallel streams it degraded far less as loss rose and finished the batch 1.49× faster at 12% loss, consistent with QUIC avoiding TCP head-of-line blocking.

For large single downloads HTTP/2 was faster in every condition, by 2.9× to over 9×. That gap should not be read as a property of HTTP/3 alone: Docker Desktop's TCP-terminating relay, curl's slow-growing HTTP/3 receive window and user-space QUIC processing all contribute, as the aioquic results and the relay's behaviour show. A test bed without the relay is the next step to separate protocol from setup.

Reproducing a condition

Set the condition on the Windows server, then run the matching demo on the client with the same values:

.\scripts\demo.ps1 net 25ms 2%                       # Windows server
./run-benchmarks.sh demo1 10.0.10.1 25ms 2%           # Kali client
./run-benchmarks.sh                                   # full run, prompts per condition
.\scripts\demo.ps1 net reset                          # Windows server, afterwards

Times are wall-clock seconds from connection start to the last byte unless noted. Loss percentages are netem's per-packet drop probability on the server's outgoing traffic.
